# Security

## Reporting

Report a security problem by opening a GitHub issue at https://github.com/anamika-iit-kgp/credora/issues with "security" in the title and the `security` label. Describe what you found, where it is in the code, and how to reproduce it. There is no bug bounty.

Because every record in Credora is synthetic, a report can include full details without exposing anyone. If you believe a finding affects the live demo at https://credora.loan in a way that could harm a visitor, say so in the issue and it will be looked at first.

## What is in scope

- The web app and its API (`frontend/`, `backend/`)
- The Exasol objects, UDFs and Lua scripts (`exasol/`)
- The deploy tool and infrastructure (`deploy/`, `infra/`, `docker-compose.yml`)
- The mock 3rd party data APIs (`mocks/`)

## What you should know

- All data is synthetic. Sapphire Bank, its customers, partners, accounts, transactions, GST returns and credit reports are generated by `mocks/generator`. No real person, company or bank record exists anywhere in the project.
- No real credentials are in the repository. Database, API and Exasol passwords are generated per deployment into AWS Secrets Manager. The demo web logins (`Demo@123`) are public on purpose, because the data behind them is synthetic.
- The live demo exposes only ports 80 and 443. Exasol's ports and SSH are open to the deployer's IP only, and the RDS databases sit in private subnets.
- Access control is enforced by Exasol. Each role, and each person's Ask Credora session, logs in as its own Exasol user, and the database refuses what the role may not read. A finding that shows a role or the AI reading beyond its grants is the most useful kind of report.
- Passwords in audited SQL are masked on the Exasol audit screen. If you find one that is not, report it.
