Credora is an ExaThon India 2026 project. It is a bank's pre-approved corporate lending, decided inside Exasol Personal, built on the Exasol Personal Local Starter Kit and deployed on AWS. It is Sapphire Bank's way to make pre-approved corporate loan offers, and the whole decision happens inside Exasol. Six sources go in. Three are bank databases read in place, and three are 3rd party APIs (CIBIL, GSTN, Account Aggregator) fetched on demand. One call to RUN_ANALYSIS comes out with an offer, a negotiation limit and a ranking for every company. It is live at credora.loan, the docs are at docs.credora.loan, and credora.link serves the 3rd party data via API.

The bank already holds the data. Offers are still slow and manual.

Sapphire Bank's credit team can't make pre-approved offers to the corporate customers it already serves, because the evidence sits in six separate systems and is gathered by hand, one company at a time. If this worked, every corporate customer would be decided in one run, and the relationship manager would call with an offer and a negotiation limit already set.

Sapphire Bank's credit team can't make pre-approved offers to the corporate customers it already serves, because the evidence sits in six separate systems and is gathered by hand, one company at a time. If this worked, every corporate customer would be decided in one run, and the relationship manager would call with an offer and a negotiation limit already set. Sapphire Bank has a large book of corporate current-account customers, and it already holds most of what it needs to lend to them. Transactions sit in Oracle core banking, partners and KYC in the MySQL customer master, the credit need on file and five thousand past loans in PostgreSQL. The rest is 3rd party data from CIBIL, GST returns and the Account Aggregator. Today a credit officer visits these one company at a time. Press next. Credora reads all six at once, inside one Exasol call, in seventeen and a half seconds for all thousand companies.

PDprobability of default

How likely the company is not to repay, from a model trained on the bank's own past loans. Graded A1 (under 1%) to D (12% and above).

RAROCrisk-adjusted return

(Rate − cost of funds − operating cost − PD × loss given default) ÷ capital held. Every offer must clear the 15% hurdle.

DSCRdebt service coverage

Cash the company generates ÷ what the loan costs it each year. At least 1.25 for the offer, 1.10 at the negotiation limit.

GSTgoods and services tax

Monthly sales each company files with the tax network, GSTN, for 2 to 10 years per company. Late filings and a gap to bank credits are warning signs.

CIBILIndia's credit bureau

A score for every partner and a commercial rank (CMR) for every company. A partner below 600 or a CMR of 9 or worse means no offer.

AAAccount Aggregator

With the customer's consent, the partners' accounts at other banks. The consent expires, so Exasol purges the data on time, with proof.

The idea is simple. Instead of waiting for customers to come in, the bank analyses the companies it already serves and approaches the best of them with a pre-approved offer. That is an amount, a rate and a tenure, plus a negotiation limit the relationship manager can move within. Six terms carry the rest of the talk. PD is the chance a company does not repay. RAROC is the return after expected loss and costs, over the capital held, and every offer must clear fifteen percent. DSCR asks whether the company's cash covers the repayments. GST returns, CIBIL and the Account Aggregator are the 3rd party evidence, fetched via API.

One engine does seven jobs, and the data never leaves it.

Why Exasol? Because one engine does seven jobs here, and we used Exasol Personal to the full, with its open-source extensions from both GitHub organisations. Federation reads the bank's databases in place through oracle-virtual-schema and adbc-vs-rs. Python UDFs fetch 3rd party data via API. UDFs train and score the models, stored in BucketFS. Lua runs the whole pipeline as one call. PREFERRING ranks. exasol-semantic-views and the preprocessor framework give one definition of every metric. And roles, grants and views decide who sees what, for people and for the AI through the Exasol MCP server. Press next for the alternative, seven separate products with the data copied between them.

Virtual schemas push the work down. Nothing is copied.

Feature step 7 aggregates core banking by account and month. Exasol hands the join, the filter and the GROUP BY to Oracle.

-- RUN_ANALYSIS, step 7 INSERT INTO CREDORA_STAGE.CA_MONTHLY SELECT t.ACCOUNT_NO, a.OWNER_ID, TRUNC(t.TXN_DATE, 'MM') MON, SUM(CASE WHEN t.DR_CR = 'C' THEN t.AMOUNT ELSE 0 END), ... COUNT(*) N FROM VS_CBS.TXN t JOIN VS_CBS.ACCOUNT a ON a.ACCOUNT_NO = t.ACCOUNT_NO WHERE a.ACCT_TYPE = 'CA' GROUP BY t.ACCOUNT_NO, a.OWNER_ID, TRUNC(t.TXN_DATE, 'MM')

Monthly totals per account come back. The ~850,000 transactions stay in Oracle, and the bank keeps one system of record.

Virtual schemas are how Exasol reads the bank without copying it. VS_CBS sits over Oracle core banking through Exasol's Oracle virtual schema adapter, from the exasol organisation. When step 7 asks for monthly totals, Exasol pushes the join, filter and GROUP BY down to Oracle, and only the totals come back. Next, MySQL and PostgreSQL go through adbc-vs-rs from exasol-labs, one Rust adapter for both engines, running in the Rust script language container from BucketFS and moving Arrow batches instead of rows. Next comes the point. The transactions never leave Oracle.

Python UDFs fetch 3rd party data via API, in 16 batches.

A SET script groups the keys into 16 buckets by the first hex digit of an MD5 hash. Exasol runs one UDF instance per bucket, 4 at a time on the node's 4 cores, and each call makes 3 attempts before it fails naming the service.

3rd party data comes in via API, through Python SET UDFs, running in Exasol's Python 3 script language container. The SQL spreads the keys over sixteen buckets, and Exasol runs one UDF instance per bucket, four at a time on the node's four cores. Each calls a bulk endpoint on credora.link, and makes three attempts before it fails naming the service. The address and token live in CONNECTION objects, never in the SQL text. That is 3,492 CIBIL reports in one second. Replies land in CREDORA_STAGE with a purge time. Next, PURGE_EXPIRED deletes them on time and keeps only a row count and a SHA-256 fingerprint as proof. The fingerprint is built per thousand-row chunk, because one run's GST rows are more than a single LISTAGG can hold.

    A failed step is logged with its error and stops the run. The last published run stays visible in the app.

    This is the heart of it. One Lua script, RUN_ANALYSIS, runs thirteen steps. It refreshes the virtual schemas, reads the credit needs on file, fetches CIBIL, GST and Account Aggregator data, computes thirteen features with an Oracle pushdown, scores with the model, flags anomalies, decides the offer and the limit, ranks with PREFERRING, and shadow-scores the challenger. Each step commits and writes a row to RUN_LOG with its row count and time, so the web app shows the run live. The 850,000 core-banking transactions are grouped by month inside Oracle through the pushdown, so feature building takes about 3.6 seconds. The whole run takes 17.5 seconds.

    The models are trained, stored and scored inside Exasol.

    Past loans are read live from PostgreSQL. Two models train on the same loans and the same hold-out. Only the active one decides.

    Machine learning never leaves the database. TRAIN_PD reads five thousand past loans live from PostgreSQL through VS_LOS, trains gradient-boosted trees with monotonic credit constraints, measures them on a hold-out, and writes the pickle to BucketFS and a row to MODEL_REGISTRY, with AUC 0.756. TRAIN_SCORECARD trains a logistic regression challenger on the same loans and the same hold-out, with AUC 0.769. Both numbers sit near the ceiling the synthetic data allows. The generator draws each default from a logistic curve over the company's hidden risk, so even a model that knew that risk exactly would score about 0.78. The scorecard beats the trees because that relationship is logistic and linear, and five thousand loans favour the simpler model. PD_SCORE checks the file's SHA-256 against MODEL_REGISTRY, loads the active pickle and scores a thousand companies in about two seconds. Next, an Isolation Forest flagged 30 unusual companies, and 4 that would have been approved were referred to a person instead. The challenger shadow-scores every run. It would change 713 grades and 62 decisions. Next, it decides nothing until the admin approves activation.

    PREFERRING ranks on three goals at once, with no weights.

    The skyline is every approved company that no other beats on return, risk and amount together. Peel it off, take the next skyline, until 50 are ranked.

    UPDATE CREDORA.DECISIONS SET SKYLINE_LAYER = :l WHERE APP_ID IN ( SELECT APP_ID FROM CREDORA.DECISIONS WHERE DECISION = 'APPROVE' AND SKYLINE_LAYER IS NULL PREFERRING HIGH RAROC_OFFER PLUS LOW PD PLUS HIGH OFFER_AMOUNT)

    On the measured run two layers held 63 companies by the time 50 were reached, in 0.03 s. The best 50 approved go to the relationship managers.

    Ranking is where Exasol's PREFERRING clause shines. Instead of inventing weights for return, risk and size, we ask for the skyline, the companies no other company beats on all three at once. Those are layer one. We mark them, ask again for the next skyline, and repeat until fifty are ranked. These dots are illustrative. On the real run two layers held 63 companies, and the whole step took three hundredths of a second.

    One certified definition serves the app, the analyst and the AI.

    CREDORA_SEM.PORTFOLIO holds certified metrics. The SQL preprocessor compiles semantic queries per role, inside Exasol.

    METRIC approval_rate AS approved_companies / NULLIF(companies_analysed, 0) ON ENTITY decision FORMAT 'percentage' DISPLAY 'Approval rate' SYNONYMS ('approval ratio', 'hit rate') RATIO PUBLIC CERTIFIED
    Numbers like the approval rate are defined once, in the semantic model CREDORA_SEM.PORTFOLIO, built with exasol-semantic-views from exasol-labs, with sixteen certified metrics with synonyms and verified questions. The web app, an analyst's SQL client and Ask Credora all read the same definition, so the AI cannot invent its own version of a metric. Next, how it works. Exasol has one SQL preprocessor slot. The preprocessor framework, also from exasol-labs, owns it and runs one rule per role. For the RM, the semantic module compiles the query into plain SQL over the latest-run views the RM may read. It costs about four milliseconds.

    Exasol, not the app, decides who sees what.

    Four people, four Exasol users, and an AI user for each with the same role. A relationship manager reads only the V_RM_* views, which return the companies assigned to CURRENT_USER.

    -- signed in to Exasol as CREDORA_RM (role R_RM)
    CREDORA_RM> SELECT * FROM CREDORA.DECISIONS;
    insufficient privileges
    CREDORA_RM> SELECT * FROM CREDORA.V_RM_DECISIONS;
    rows, the companies assigned to
    CREDORA_RM, from published runs
    CREATE VIEW CREDORA.V_RM_DECISIONS AS SELECT d.* FROM CREDORA.DECISIONS d JOIN CREDORA.RM_ASSIGNMENT a ON a.CIF_ID = d.CIF_ID AND a.EXA_USER = CURRENT_USER JOIN CREDORA.RUN_PUBLISH p ON p.RUN_ID = d.RUN_ID;

    The view runs with its owner's rights, so R_RM needs no grant on the tables underneath. A second manager, CREDORA_RM002, and the RM's AI user CREDORA_RM_AI run the same SELECT in the control room's proof panel. With one Exasol user per RM the views work unchanged.

    Access is enforced by the database. Each role has its own Exasol user, and every screen reads as that user. Each person's Ask Credora session has an AI user of its own with the same role, and the control room proves the row filter by running one SELECT as the RM, as her AI user and as a second manager. The rings show reach. Admin and data scientist see raw 3rd party data. Loan operations sees the bank databases and all results. The relationship manager sees only the V_RM views. Next, the RM tries to read DECISIONS directly, and Exasol answers insufficient privileges. Next, the RM reads V_RM_DECISIONS instead, which joins the assignments on CURRENT_USER, and gets exactly the companies loan operations assigned, at full detail. In the demo that is a book of 25 companies.

    Ask Credora logs in as you, so the AI cannot read more than you.

    Claude reaches Exasol only through the official Exasol MCP server (exasol/mcp-server), started for each question on the app host as the signed-in person's own AI user, which holds the same role and sits in a low-priority consumer group.

    Ask Credora is plain-English questions over the analysis. Watch the role travel. In step one the question arrives with the login token, here as the RM. In two and three a topic gate asks Claude, with no tools, whether this is about Credora, and anything else is refused before Exasol is touched. In four and five exasol_login maps the role to the person's AI user, and the backend starts the official Exasol MCP server, from the exasol organisation, as CREDORA_RM_AI with writes switched off. That user holds the RM's role and sits in the CREDORA_AI consumer group, with a sixty second limit and two gigabytes of memory, so the AI cannot starve the analysis. In six to nine Claude picks tools and writes SQL, and Exasol checks the RM's grants on every statement. In ten to twelve the answer comes back with every SQL statement it ran. A jailbroken prompt still cannot read more than the person who signed in.

    From a published run to a disbursed loan, in four roles.

    Each hand-off is a row in Exasol or the CRM, so admin, data scientist and loan operations can track every company.

    Here is the people side, end to end. The data scientist trains models and runs what-if on policy, but cannot switch them on. The admin approves model activation and policy proposals, which writes the new CONFIG and starts an official rerun as the service user. The data scientist publishes the run. Loan operations assigns companies to relationship managers. The RM sees only the assigned companies, at full detail, negotiates inside the limit, and logs the status from contacted to disbursed. Admin, data scientist and loan operations track every company along the way.

    Narrow doors, and failures that stay contained.

    Network

    Only 80 and 443 are public. Exasol's ports open to admin IPs only, and RDS sits in private subnets.

    Database grants

    A user per role. A refused query reaches the app as 403 Exasol denied access for your role.

    AI in the same boundary

    MCP writes off, an AI user per person in a low-priority consumer group, a topic gate before any query, every SQL statement shown with the answer.

    Secrets

    Generated per deployment into Secrets Manager. API tokens live in CONNECTION objects. None in the repo.

    Consent and retention

    3rd party replies carry a purge time. PURGE_EXPIRED deletes them and keeps a SHA-256 proof per 1,000-row chunk.

    What I learnt about Exasol Personal.

    Six things the build taught me. Each one is now in the code or the docs.

    Pushdown is worth checking function by function

    The Oracle adapter does not push TRUNC(date, 'MM'), so step 7 groups by TO_CHAR(date, 'YYYY-MM'). That took the run from 24.7 s to 17.5 s.

    EXPLAIN VIRTUAL makes pushdown provable

    The Sources screen shows the SQL each database receives, so the claim is Exasol's own. It is also how the TRUNC gap was found.

    The java-17 container loses DNS after a restart

    It has no /etc/resolv.conf or /etc/hosts. exasol/hotfix/slc_dns_fix.sh links both to the node's /conf files again after every Exasol restart.

    LISTAGG stops at 2,000,000 characters

    One run's GST rows are more than that, so the purge fingerprint is built per 1,000-row chunk, and the proof is the hash of the chunk hashes.

    The MCP server can log in as any user

    So the AI gets the person's own rights and nothing more. A prompt cannot widen what Exasol grants.

    Consumer groups are per user

    So the AI got its own users, one per person with the same role, in a low-priority group with a 60 s limit and 2 GiB of memory.

    Six things I learnt about Exasol Personal while building this. First, pushdown is worth checking function by function. The Oracle adapter does not push TRUNC of a date to the month, so step seven groups by TO_CHAR instead, and the run went from twenty-four point seven seconds to seventeen and a half. Second, EXPLAIN VIRTUAL makes pushdown provable, and it is how that gap was found. Third, the java-17 script language container loses DNS after an Exasol restart, and a small hotfix script re-adds the resolv.conf links. Fourth, LISTAGG stops at two million characters, so the purge fingerprints are chunked. Fifth, the MCP server can log in as any user, so the AI gets exactly the person's rights. Sixth, consumer groups are per user, so the AI got its own users. All six are in the code and the docs.
