Credora for Sapphire Bank

Sapphire Bank has a large book of corporate current-account customers, each with 2 to 5 partners. The demo data set starts at 1,000 companies and the admin can add more with one click. Instead of waiting for companies to come in, the bank approaches its best customers with a pre-approved offer. Credora brings the bank's own data and 3rd party data via API on every company and partner (CIBIL, GST and Account Aggregator) into Exasol. Exasol scores each company with an ML model it trained itself, gives it a decision, an offer (amount, ROI, tenure) and a negotiation limit, and ranks the best 50 for the relationship managers.

Exasol is the analytics (OLAP) platform. The bank's data stays in three RDS databases (Oracle, MySQL, PostgreSQL) and is read in place through virtual schemas. CIBIL, GSTN and the Account Aggregator are mock APIs, because this is a project and not connected to the real services. Everything runs on AWS from one repo with one command. The working application is live at https://credora.loan (docs at https://docs.credora.loan). The mock 3rd party data APIs, which Exasol's UDFs call on demand, are at https://credora.link.

Every role reads Exasol as its own database user, and so does the AI. Ask Credora's MCP server logs in as the signed-in person's own AI user, which holds the same role, so Exasol's grants decide what each screen and each answer can contain. Demo logins admin, datasci, loanops, rm, password Demo@123, one click on the sign-in page.

All data is synthetic, created by the built-in mock data generator.

Each month has GSTR-1 turnover, GSTR-3B tax paid, due date and filing date (unfiled returns are empty). The GSTIN registration date matches the history.

A CIBIL report, as it usually looks

  • Partner (consumer). Name, PAN, date of birth, score 300–900 (or no history), accounts (lender, type, sanctioned amount, balance, overdue, 36-month DPD history), enquiries in the last 6 and 12 months.
  • Company (commercial). CMR rank 1–10, total exposure, overdue, number of facilities, suit-filed and wilful-default flags.
  • A hidden "true risk" per company drives the data consistently. Risky companies file GST late, bounce more, show a bigger gap between GST turnover and bank credits, and have partners with lower scores.

Roles and who sees what

Four roles, four Exasol users. Each role reaches a ring of data. The relationship manager's ring is cut down to her assigned rows by Exasol itself (row-level security views on CURRENT_USER). Ask Credora carries the signed-in role into Exasol, so the database decides what the AI can read. The work passes from role to role. The data scientist runs and publishes, loan operations assigns, the relationship manager works and logs the loan status, and the admin approves policy and model changes (full-page diagram).

Ask Credora inside the same boundary

Ask Credora starts the official Exasol MCP server (exasol-mcp-server 2.3.0, writes switched off) for each question, logged in as the signed-in person's own AI user, which holds the person's role and sits in the CREDORA_AI consumer group. The prompt describes the data a role may read, but Exasol's grants enforce it, and the database refuses a query outside them. A one-word topic check runs before any tool use, so unrelated questions never reach Exasol. Every answer lists each MCP tool call with the exact SQL it ran. The code is in backend/app/assistant.py exasol_login().

Explain mode shows what Exasol does at every click

A switch in the web app's top bar, on by default and remembered per viewer. Off, Credora is a plain CRM. On, it shows the database behind every screen, for readers who know databases better than banking.

  • Hints and a band per screen. An information mark next to key numbers, labels and buttons (PD, RAROC, grade, hard fails, rank, the model version, the semantic metrics, the role, publish, assign, approve, Ask Credora) opens the term in plain words and in Exasol's terms, with its objects, the code that runs and links to the Exasol documentation. Under each page header a band says what Exasol is doing on that screen. The content lives in frontend/src/explain/ (glossary.ts, pages.ts, actions.ts), and the Glossary page lists every term.
  • Action notes. Starting an action (run analysis, publish, train, request or approve an activation, what-if, propose or approve a policy, assign, log a status, generate data, credit memo, Ask Credora) shows its steps in Exasol and the Exasol user it runs as. Job progress names the Exasol object of each step.
  • Exasol console. A bottom drawer that lists, live, every statement the backend ran in Exasol for this browser tab, with time, Exasol user (CREDORA_RM, CREDORA_SVC and so on), SQL, milliseconds, rows and any error. exa.query and the jobs' statements are recorded in a ring buffer of the latest 200 per signed-in person (backend/app/console.py). Jobs add each RUN_ANALYSIS step as it commits and each model registry switch. Ask Credora adds each MCP tool call as "Claude, exasol-mcp-server on the EC2 app host, Exasol as the role's user". Passwords, keys and secret-looking literals are masked. Each person reads only their own entries (GET /api/exasol/console), and the admin may also read everyone's.
  • Exasol control room. A page for every role (GET /api/exasol/control-room) that maps the database from its system tables, read with the signed-in role's own Exasol user. It shows schemas and object counts, virtual schemas with adapter and last refresh, scripts with their language containers, connection names, the model registry with each pickle in BucketFS, roles and grants, the SQL preprocessor, the semantic model's 16 certified metrics, the latest run's steps, and for the admin the live sessions. What a role's grants hide is missing, and a refused read is shown as Exasol's refusal. Each piece names the Exasol open-source project behind it.

ML and AI inside Exasol

The risk model is trained and scored by Python UDFs in Exasol's PYTHON3 script language container, with scikit-learn. The training data is read live from PostgreSQL through VS_LOS, and the data never leaves the database to be scored.

ObjectKindJob in Credora
TRAIN_PD (SET UDF), run by Lua TRAIN_MODELscikit-learn HistGradientBoostingClassifier with monotonic constraints (for example, more late GST filings can only raise risk)Trains on 5,000 past loans, measures AUC, Gini and permutation importance on a hold-out set, saves models/pd_<version>.pkl to BucketFS and registers it in MODEL_REGISTRY. The champion is model v3, with AUC 0.756 and Gini 0.512 on the hold-out set.

  • Ranking. Exasol's PREFERRING HIGH RAROC_OFFER PLUS LOW PD PLUS HIGH OFFER_AMOUNT returns the skyline of approved companies that no other company beats on return, risk and size at once. Peeling off skyline after skyline gives layers, and the best 50 go to the RMs. No hand-tuned weights.
  • Models are versioned, champion against challenger. Each training adds a champion and a challenger. The data scientist compares AUC, Gini, top features or coefficients and the decisions that would change on the current run, and requests activation of one. The admin approves or rejects it, and no model decides until then. RUN_ANALYSIS trains v1 itself if no model exists.

How one company is decided

Policy values live in CREDORA.CONFIG, so the data scientist can change them in a what-if. EBLR 8.25%, operating spread 0.75%, cost of funds 6.50%, opex 1.00%, unsecured LGD 45%, capital 12%, hurdle RAROC 15%, exposure cap 60% of GST turnover. The cash margin per industry and the LGD per collateral type come from CREDORA.INDUSTRY_MARGIN and CREDORA.LGD_COLLATERAL (docs/PRICING.md).

StepWhat happensIn Exasol
1 · CombineCredit need on file (PostgreSQL) joined with company and partners (MySQL), in placeCREDORA.APPLICATIONS
2 · Features13 features. GST years, turnover, late filings, GST-vs-bank gap, average balance, inflow volatility, bounce ratio, CMR rank, partners' minimum and average score, overdue, other-bank balance, DSCRWindow functions over CA_MONTHLY (aggregated in Oracle) and the API data → FEATURES
3 · RiskProbability of default, grade, per-feature attributionPD_SCORE → SCORES
4 · Hard failsWilful defaulter, CMR rank 9 or worse, 4+ late GST returns in 12 months, any partner CIBIL below 600, bounce ratio above 8%SQL
5 · ROIEBLR + risk spread by grade (1.00% for A1 to 7.00% for D) + operating spread, minus 0.25% if collateral covers the loan, never below the floor. 6 · AmountA term loan gets what the industry's cash margin on GST turnover (5% to 22%) can repay at DSCR 1.25. Working capital gets the smaller of 20% of GST turnover and the same cash-flow cap. 7 · TenureA term loan gets the indicated tenure, up to 84 months (60 for grades C1, C2, D). Working capital gets 12 months.SQL

Deployment on AWS

Credora was first built on the Exasol Personal Local Starter Kit (exakit 0.2.3) on a laptop. It was then deployed to AWS with the Exasol Personal launcher 2.3.0, which runs Exasol 2026.1.0 on one r6i.xlarge node. One command, python deploy/credora.py deploy --env <name>, builds everything below in any AWS account.

Drawn in the AWS architecture-diagram style, with AWS Cloud, then Region, then VPC, then subnets, then security groups, with service icons in AWS category colours. The icons are simplified redraws, not the official icon files. Numbered arrows are explained below the diagram.

  1. Users → Route 53. The domain root and www resolve to the app host's Elastic IP.
  2. Users → app host. HTTPS through the internet gateway to Caddy, which serves the React app at the domain root, sends /api to the backend, and redirects www and HTTP to https://<DOMAIN>.
  3. Backend → Exasol. SQL on :8563 over the VPC, logged in as the Exasol user of the signed-in role. Ask Credora queries through the Exasol MCP server as the same role user.
  4. Exasol → mock 3rd party APIs. Python UDFs fetch 3rd party data from CIBIL, GSTN and AA on the app host's private IP, ports 8101–8103 (open to the VPC only).
  5. Exasol → RDS. The virtual schemas read Oracle (:1521), MySQL (:3306) and PostgreSQL (:5432) in place.
  6. Generator → RDS (dashed). Writes the bank data into Oracle, MySQL and PostgreSQL, and the CIBIL, GST and AA data into mockdb.
  7. Backend → PostgreSQL crm. Offers, negotiation steps and sanction (small, frequent writes).
  8. Generator → S3 (dashed). The hidden truth per company, for the admin scorecard.
  9. Deployer → Exasol and app host (dashed). Exasol ports 22, 2581, 8443 and 8563, and SSH to the app host, only from the deployer's IP.

Not drawn as arrows. On start, the app host reads the runtime secret from Secrets Manager with its instance role and writes it to .env.runtime for the containers. RDS is not publicly accessible, and its subnet group spans two zones.

How it works, step by step

  1. AdminClicks Generate new mock data and confirms "Generating new mock data will clear all the existing data".
  2. GeneratorTruncates every table, then loads 1,000 companies, about 3,500 partners, about 850,000 Oracle transactions, CIBIL reports for every partner and company, 2–10 years of GST, partners' other-bank accounts and 5,000 past loans. About 75 seconds.
  3. EveryoneCan browse the new data in the data explorer (as far as their role allows), with each item tagged by its source.
  4. Data scientistOptionally trains a new champion and challenger (TRAIN_MODEL → TRAIN_PD and TRAIN_SCORECARD), compares them on the same hold-out and on the decisions that would change, and requests activation of one with a note.
  5. AdminApproves or rejects the activation request under Approvals. Only an approval switches MODEL_REGISTRY.IS_ACTIVE. The same screen holds policy proposals the data scientist sent from a saved what-if run. Approving one writes CONFIG, runs the analysis and publishes it in one job.
  6. Data scientistClicks Run analysis. The backend runs EXECUTE SCRIPT CREDORA.RUN_ANALYSIS('<run>') as CREDORA_SVC, and the 13 steps below take about 17.5 seconds for 1,000 companies. The run is a draft.
  7. Data scientistReviews the draft and clicks Publish to loan operations. CREDORA.RUN_PUBLISH gets the run, its offers go to the CRM, and it becomes the official run for loan operations, the RM views, V_LATEST_* and the semantic view.
  8. Loan operationsSees New results published, opens Decisions or the Top 50, selects companies and clicks Assign to RM, and CREDORA.RM_ASSIGNMENT gets each company with the manager's Exasol user. Opens the Exasol report for any company, with the decision, why, how and which source each number came from.
  9. Relationship managerSees only her assigned companies (V_RM_* views filtered on CURRENT_USER), at full detail, and logs the loan status as she talks to each customer.
  10. Exasol · AIOn demand from a company report, CREDIT_MEMO writes a short credit memo inside Exasol through CONNECTION AI_LLM.
  11. Any roleAsks Ask Credora a question. Claude answers through the Exasol MCP server, logged in as that role's Exasol user, and shows every SQL statement it ran.
  12. Relationship managerQuotes and proposes terms with the customer, and Exasol checks them against the limit and RAROC. Above the limit the offer is escalated.
  13. Loan operationsVerifies and sanctions (maker-checker). PostgreSQL crm records each stage.
  14. Admin · DS · LOFollow every assigned company on the Loan status tracker, with its manager, current status, last update and history, filterable by manager and status, exportable as CSV.
  15. Exasol · purgeEvery 15 minutes the Exasol Scheduler runs PURGE_EXPIRED from SCHED.SCHED_TASKS. It deletes raw API data past its purge time, and the row count and SHA-256 fingerprint are kept in PURGE_LOG as proof, and the run in SCHED.SCHED_HISTORY. Every statement of every step is also in Exasol's audit log, tagged with the app user and screen.

One repo, one command

The repo is the submission. It holds the web app, backend, mock APIs, generator, infrastructure, every Exasol script and UDF, and the ML code. Anyone with an AWS account fills in an env file and runs one command to recreate the whole system.

Only AWS_PROFILE and DOMAIN are required. The hosted zone is looked up from DOMAIN. Database, API-token and Exasol-user passwords are generated by OpenTofu into Secrets Manager. A filled copy (.env.credora) stays on the deployer's machine.

python deploy/credora.py deploy --env <name> (or make deploy ENV=<name>) does everything

  1. CheckReads .env.<name> and gets AWS credentials from the CLI profile.
  2. ExasolThe official exasol launcher (init aws ubuntu, then deploy) creates the VPC and the Exasol EC2, after its ports are restricted to the deployer's IP.
  3. AWS infraOpenTofu, run in Docker, adds two private subnets, RDS for Oracle, MySQL and PostgreSQL, the app host with its Elastic IP and IAM role, S3, the Secrets Manager runtime secret and the Route 53 A records for the domain root and www.
  4. ShipBuilds the React frontend, copies the repo to the app host, writes .env.runtime from the secret and starts Docker Compose (Caddy, backend, generator, mock APIs, mockdb).
  5. GenerateCalls the generator for 1,000 companies of mock data in the three bank databases and the mock APIs.
  6. ExtensionsUploads the Rust SLC to BucketFS and registers RUST, then installs adbc-vs-rs (adapter and scan UDF), the Oracle virtual schema jar and ojdbc17.
  7. Exasol SQLCreates roles, schemas, connections, UDFs and Lua scripts, AI_LLM if a key is set, then the three virtual schemas, grants and the six users.
  8. First analysisLogs in to the API as admin and runs the analysis. It trains model v1 because none exists.
  9. DonePrints the site address (https://<DOMAIN>), the logins, the Exasol address and each container's status.

Safe to re-run. Parts can be run alone with ship, exasol, generate, status. destroy removes the OpenTofu resources and the Exasol deployment.

  • No account IDs, zone IDs, ARNs, IPs, bucket names or domains in code. Everything comes from the env file or is looked up at deploy time.
  • The domain is set once, in DOMAIN. Caddy, Route 53, the app and the API all read it.
  • Each deployment has its own infrastructure state (infra/state/<name>/) and its own secrets in its own account.
  • Data is synthetic and regenerated, and the model is retrained, so moving needs no data copy.
  • Steps to move are in docs/PORTING.md.
