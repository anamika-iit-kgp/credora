# Why Exasol

Credora is a working application built on Exasol Personal for ExaThon India 2026, live at https://credora.loan. Docs are at https://docs.credora.loan and the mock 3rd party data APIs at https://credora.link.

To make pre-approved offers, a bank has to read three of its own databases, pull credit bureau, GST and Account Aggregator data by API, build features, train and run risk models, rank the companies, and control who sees what. Exasol already had a feature or an official integration for every one of those jobs, so Credora could be built by plugging them together instead of writing connectors, pipelines and an ML platform. And because Exasol is an in-memory, columnar, massively parallel analytics database, the whole analysis is fast enough to run on demand.

## What the bank needed, and what Exasol already had

| The bank needed to | Exasol feature or integration | Measured on the live deployment |
|---|---|---|
| Read core banking, the customer master and loan origination without copying them | Virtual schemas for Oracle (Java adapter) and for MySQL and PostgreSQL (adbc-vs-rs on the Rust script language container) | 3 virtual schemas refreshed in 1.8 s. 850,000 Oracle transactions grouped in Oracle (pushdown) in 3.6 s |
| Fetch 3rd party data on demand via API | Python SET UDFs with secrets kept in CONNECTION objects | 3,492 CIBIL reports in 1.0 s and 71,665 GST returns in 1.6 s, in 16 batches of keys that Exasol runs 4 at a time on the node's 4 cores |
| Build model features over transactions and GST history | Analytic SQL with window functions and CTEs | 13 features for 1,000 companies in one step |
| Train and run risk models where the data is | Python UDFs with scikit-learn, models stored in BucketFS | 1,000 companies scored in 1.9 s. Anomaly check in 1.3 s. Challenger shadow score in 1.7 s |
| Run the whole process as one auditable call | Lua scripting with a commit and a log row per step | 13 steps for 1,000 companies in 17.5 s on one `r6i.xlarge` node |
| Rank companies on risk, return and size together | `PREFERRING` skyline queries | Top 50 ranked in 0.03 s |
| Give the app, analysts and the AI one definition of each number | Semantic views (exasol-labs) behind the preprocessor framework | 16 certified metrics in `CREDORA_SEM.PORTFOLIO` |
| Let each person and the AI see only what they may | Users, roles, grants and row-level security views on `CURRENT_USER`, with an AI user per person | A relationship manager reads 25 rows, the rest is refused by Exasol, for her screens and for her AI user alike |
| Let an AI assistant query the data safely | The official Exasol MCP server, logged in as the person's own AI user, with the same role, in a low-priority consumer group | Every answer shows the SQL it ran |
| Prove what happened, for a regulator | The audit log, `EXPLAIN VIRTUAL`, `COMMENT ON`, consumer groups and the Exasol Scheduler | Every statement tagged with the app user and screen |
| Build it once and run it anywhere | The Exasol Personal Local Starter Kit, then the Exasol Personal launcher on AWS | One command deploys the whole system |

The rest of this page lists every Exasol feature the project uses, where it is in the code, and why it fits the job.

## Every feature, where it is and why

| 1 | **Virtual schema for Oracle** (Java adapter, JDBC) | [03_virtual_schemas.sql](../exasol/sql/03_virtual_schemas.sql) | `VS_CBS` reads 850,000 core-banking transactions in Oracle in place | Core banking is never copied. Banks keep their system of record where it is. |
| 2 | **Virtual schema with adbc-vs-rs** (Rust, ADBC, Arrow) | same | `VS_CIF` on MySQL and `VS_LOS` on PostgreSQL | One adapter for two engines, moving Arrow record batches, not rows |
| 3 | **Rust script language container** | [exasol_setup.py](../deploy/exasol_setup.py) `install_rust_slc` | The exasol-labs language-container-rs release 0.23.1, uploaded to BucketFS as is and registered as `RUST` | Runs the Rust adapter at the SDK version it was built for, with no container build of our own |
| 4 | **BucketFS** | `exasol_setup.py`, [05_ml_udfs.sql](../exasol/udf/05_ml_udfs.sql) | Holds the SLC, adapter library, ADBC drivers (fetched on first use), the Oracle JDBC driver, and every trained model version | One distributed file store for code, drivers and models |
| 5 | **Python UDFs calling APIs** (SET scripts) | [04_api_udfs.sql](../exasol/udf/04_api_udfs.sql) | 3rd party data from CIBIL, GSTN and the Account Aggregator, fetched on demand via API through bulk endpoints. The keys are spread over 16 batches (one hex digit of an MD5), and Exasol runs the UDF instances 4 at a time on the node's 4 cores. Each call makes 3 attempts, with 1 s and 2 s pauses, and then fails with an error that names the service. 3,492 CIBIL reports arrive in 1.0 s | 3rd party data comes in with SQL, in batches, and lands next to the bank data |
| 6 | **CONNECTION objects** | [02_connections.sql](../exasol/sql/02_connections.sql) | API addresses, tokens and database credentials | Secrets never appear in SQL text, and access is granted per role |
| 7 | **ML training inside the database** | `TRAIN_PD` and `TRAIN_SCORECARD` in 05_ml_udfs.sql | One `TRAIN_MODEL` call trains two models on 5,000 past loans read live from PostgreSQL and measures both on the same 25% hold-out. The champion is gradient-boosted trees with monotonic credit constraints (AUC 0.756, Gini 0.512, permutation importance). The challenger is a logistic regression scorecard on standardised features (AUC 0.769, Gini 0.538, signed coefficients). Both land in `MODEL_REGISTRY` (primary key `MODEL_VERSION`) and BucketFS, with a SHA-256 of each model file in `MODEL_SHA256`. Both AUCs sit near the ceiling the synthetic data allows. The generator (`mocks/generator/generator/risk.py`) draws each default from Bernoulli(sigmoid(-3.05 + 1.25 z)), with z the company's hidden risk, so even a model that knew z exactly would score about 0.78. The scorecard beats the trees because that relationship is logistic and linear in z, and 5,000 loans favour the simpler model | No data export to a separate ML platform, and a simpler, explainable model is always measured against the champion |
| 8 | **ML scoring with explanations** | `PD_SCORE` | Probability of default for 1,000 companies in about 2 seconds, plus the effect of each feature on each company. The same UDF scores either model. Before it unpickles a model file from BucketFS it hashes the file and refuses a mismatch with `MODEL_REGISTRY.MODEL_SHA256` | Every decision can say why, and only the registered model file is ever loaded |
| 8a | **Champion/challenger in the shadow** | `SCORE_CHALLENGER` and `DECISION_LOGIC` in [06_run_analysis.sql](../exasol/lua/06_run_analysis.sql) | Step 13 of every run scores the companies with the inactive model and runs the decision SQL again on its PD (one Lua library holds that SQL for both), writing `CHALLENGER_SCORES`. On the last run the scorecard would change 713 of 1,000 grades and 62 decisions. It decides nothing until a data scientist activates it | A model change is judged on today's companies, in about 1.7 s, before it touches an offer |
| 8b | **Unsupervised anomaly detection in a UDF** | `ANOMALY_FLAG` in 05_ml_udfs.sql, step 10 of RUN_ANALYSIS | An Isolation Forest in one UDF instance sees all 1,000 companies of the run at once and flags the most unusual 3% (CONFIG `ANOMALY_CONTAMINATION_PCT`) on GST turnover against bank credits and balances, inflow volatility and partners' money at other banks, with the figures that stand out, in about 1.3 s. A flagged company that would be approved is referred with an "Anomaly" reason, and it is never declined on the flag | Possible circular trading or inflated turnover gets a person's eye, inside the same run |
| 9 | **Lua scripting** | [06_run_analysis.sql](../exasol/lua/06_run_analysis.sql) | `RUN_ANALYSIS` runs 13 logged steps in 17.5 s, committing each one. A step that fails is committed to `RUN_LOG` with its error before the run stops. `TRAIN_MODEL` trains and versions both models | The whole pipeline is one database call, with a timing for each step and a visible failure |
| 10 | **Analytic SQL** with window functions, CTEs and pushdown aggregation | step 7 of RUN_ANALYSIS | 13 features exactly as in [DATA_MODEL.md](DATA_MODEL.md) section 8. Oracle groups the ~850,000 transactions per account and month (join, filter and `GROUP BY` pushed down, about 19,000 rows return) | Feature logic is SQL anyone can read and audit |
| 11 | **`PREFERRING` (skyline queries)** | step 12 of RUN_ANALYSIS | Peels Pareto layers of companies that are best on return, risk and amount together, and the top 50 go to RMs | Multi-criteria ranking with no hand-tuned weights |
| 12 | **Roles, users and grants** | [07_security.sql](../exasol/sql/07_security.sql), [backend/app/exa.py](../backend/app/exa.py) `ROLE_USER` | One Exasol user per app role, `CREDORA_ADMIN`, `CREDORA_DATASCI`, `CREDORA_LOANOPS` and `CREDORA_RM`, plus one AI user per person with the same role, `CREDORA_ADMIN_AI`, `CREDORA_DATASCI_AI`, `CREDORA_LOANOPS_AI` and `CREDORA_RM_AI`, and a second manager, `CREDORA_RM002`. The backend runs every read for a signed-in person as that user, Ask Credora runs as the AI user, and jobs run as `CREDORA_SVC`. The admin's AI user has no dictionary access, so the AI cannot read the audit log. Loan operations cannot read the raw API data (`CREDORA_STAGE`). RMs have no grant on the result tables at all, only on the row-level security views of row 20. A refused query returns `403` to the UI | Access is enforced by the database, not only by the app |
| 13 | **Purge with proof** | [08_purge.sql](../exasol/lua/08_purge.sql) | Raw CIBIL, GST and AA replies are deleted at their purge time, with row counts and a SHA-256 fingerprint kept. The rows of a run are sorted by key and cut into chunks of 1,000, each chunk is hashed, and the fingerprint is the hash of the chunk hashes, because one run's GST rows would push a single LISTAGG past Exasol's 2,000,000-character VARCHAR limit. On the live data that is 72 chunks of up to 33,325 characters per run. The purge skips while an analysis logged a step in the last 3 minutes, because steps 3 to 6 write the same tables. The Exasol Scheduler runs it every 15 minutes (row 26) | Consent-based data (Account Aggregator) must not be kept, and an auditor can recompute the proof |
| 14 | **Generative AI from a UDF** | [09_ai_udf.sql](../exasol/udf/09_ai_udf.sql), [backend/app/memo.py](../backend/app/memo.py) | `CREDIT_MEMO` asks Claude (`claude-sonnet-5-5`) for a short credit memo per company through `CONNECTION AI_LLM`, on demand from the Exasol report page (engine `exasol-udf`). ## An ecosystem of building blocks

Exasol is more than a database engine. Around it, the [exasol](https://github.com/exasol) and [exasol-labs](https://github.com/exasol-labs) GitHub organisations publish open-source building blocks, such as virtual schema adapters, script language containers, drivers, an MCP server, a preprocessor framework, a semantic layer and the Exasol Personal launcher. A custom solution picks the blocks it needs and plugs them together, like Lego, instead of building connectors and runtimes itself. Credora is assembled this way.

| Building block | Repository | Used in Credora for |
|---|---|---|
| Personal local starter kit | [exasol-labs/exasol-personal-local-starterkit](https://github.com/exasol-labs/exasol-personal-local-starterkit) | Local prototyping before the cloud build, with MCP setup, exapump and pyexasol |
| Exasol Personal launcher (`exasol` CLI, AWS and Ubuntu presets) | [exasol/exasol-personal](https://github.com/exasol/exasol-personal) | Installing Exasol on EC2 with one command, from the deploy tool |
| Oracle virtual schema | [exasol/oracle-virtual-schema](https://github.com/exasol/oracle-virtual-schema) | `VS_CBS`, core banking read in place |
| Virtual schema framework and dialects | [exasol/virtual-schemas](https://github.com/exasol/virtual-schemas) | The adapter model both virtual schemas follow |
| ADBC virtual schema (Rust) | [exasol-labs/adbc-vs-rs](https://github.com/exasol-labs/adbc-vs-rs) | `VS_CIF` on MySQL and `VS_LOS` on PostgreSQL, one adapter for both |
| Rust script language container | [exasol-labs/language-container-rs](https://github.com/exasol-labs/language-container-rs) | The runtime the ADBC adapter runs in, pinned to 0.23.1 |
| Built-in Python 3 and Java script languages | [exasol/script-languages-release](https://github.com/exasol/script-languages-release) | API, ML and AI UDFs (Python) and the Oracle adapter (Java) |
| pyexasol | [exasol/pyexasol](https://github.com/exasol/pyexasol) | The backend's and the deploy tool's connection to Exasol |
| Exasol MCP server | [exasol/mcp-server](https://github.com/exasol/mcp-server) | Ask Credora. Claude queries Exasol through MCP as the signed-in role's Exasol user, with writes off, pinned to 2.3.0 |
| Preprocessor framework | [exasol-labs/preprocessor-framework](https://github.com/exasol-labs/preprocessor-framework) | Owns the one system SQL preprocessor slot and dispatches per role, pinned to v0.9.1 |
| Semantic views | [exasol-labs/exasol-semantic-views](https://github.com/exasol-labs/exasol-semantic-views) | The semantic model `CREDORA_SEM.PORTFOLIO` and its compiler, plugged into the framework as a module, pinned to v0.5.1 |
| Preprocessor library | [exasol-labs/preprocessor-library](https://github.com/exasol-labs/preprocessor-library) | `cast_shorthand` and `trailing_comma` for the roles that send AI-written SQL, pinned to v0.3.1 and its artifact SHA-256 |
| Exasol Scheduler | [exasol-labs/exasol-scheduler](https://github.com/exasol-labs/exasol-scheduler) | The consent purge every 15 minutes and the nightly virtual-schema refresh, from `SCHED.SCHED_TASKS`, pinned to v0.4.1 and its release SHA-256 |
| UDF mock | [exasol/udf-mock-python](https://github.com/exasol/udf-mock-python) | CI runs the deployed `ANOMALY_FLAG` and `PD_SCORE` code without a database, pinned to 0.5.0 |

Each block is independent and versioned, so one can be upgraded or swapped without touching the others. The deploy tool pins the version of every block it downloads. Credora's own code adds only the bank-specific parts, which are the data model, the API and ML UDFs, the decision logic in Lua, the web app and the infrastructure.

The challenger scorecard (v3-lr) would have changed 713 grades and 62 decisions (42 refer to approve, 20 approve to refer).

### Scale-up, the same run at 1,000, 10,000 and 50,000 companies

## Banking notes

The design follows a few regulatory anchors. Only the ones I am sure of are named here.

- Working-capital limits follow the Nayak committee's turnover method. The policy key `MAX_GST_SHARE_PCT` in `CREDORA.CONFIG` (20% by default) caps the working-capital offer as a share of the company's 12-month GST turnover, and DSCR caps it again.
- Bureau pulls are consent-based, as the Credit Information Companies (Regulation) Act, 2005 (CICRA) requires. The CIBIL UDFs fetch reports for the bank's own customers only, and every raw reply carries a purge time.
- Account Aggregator data comes with a consent purpose and a data life. The consent's expiry sets `PURGE_AT` on every staged AA row, and `PURGE_EXPIRED` deletes the rows on time and keeps a fingerprint as proof.
- Model risk follows the RBI's 2024 guidance on model risk management for credit. Two models train on the same loans and the same hold-out, the challenger is scored in the shadow on every run, and a new version decides nothing until the admin approves its activation.

Limitations. The offer carries no Key Facts Statement (KFS) and no annual percentage rate (APR) field. Both would be needed before a real customer saw the offer.

## SQL preprocessing and the semantic layer

How the two blocks fit together.

- `deploy/credora.py exasol` installs [preprocessor-framework](https://github.com/exasol-labs/preprocessor-framework) v0.9.1 (`release.sql`, sha256-pinned) and [exasol-semantic-views](https://github.com/exasol-labs/exasol-semantic-views) v0.5.1 (the release's own installer, from its prebuilt `build/install/`), then the module, the latest-run views and the model, and last sets `ALTER SYSTEM SET SQL_PREPROCESSOR_SCRIPT = PREPROC_RT.MASTER` after trying it in one session.
- The semantic views project ships its own preprocessor, `SEMANTIC_ADMIN.SEMANTIC_PREPROCESSOR`, written to own the slot. The framework lists the integration as a follow-on and ships no module for it. Credora follows the framework's "bring your own preprocessor" contract. `PREPROC_RT.SEMANTIC_VIEWS_V1` is a function that takes the statement and returns the semantic compiler's SQL, or nothing. It is registered with `PREPROC.MODULE_REGISTER` (`self-deployed`, fronting exasol-semantic-views v0.5.1) and one `PREPROC.RULE_ENSURE` per role. A semantic query the layer refuses fails with the layer's own message (for example `SEMANTIC_QUERY_020: Unknown semantic field`).
- A role user's ordinary statement costs about 4 ms, for one lookup in `SYS.EXA_ALL_TABLES` for a `SEMANTIC_DISCOVERY` table in the schemas the statement reads. (An earlier version selected from `<schema>.SEMANTIC_DISCOVERY` directly and left a failed statement in the audit log for every miss.) The compiler is loaded only for statements that read `CREDORA_SEM`.
- The preprocessor-library modules `cast_shorthand` and `trailing_comma` run in the TRANSLATE phase for the same roles, before this EXPAND module, so `avg_pd::DECIMAL(6,4)` in semantic SQL arrives as a plain `CAST`.
- Ask Credora needs no preprocessor tools. Every MCP database session, whichever role user it logs in as and including the new one the MCP server opens after a failed query, gets semantic SQL from the system setting and that role's rule. The tools are switched off (`enable_preprocessor_tools: false`).

Checks.

```sql
SELECT * FROM PREPROC_RT.MY_PIPELINE;            -- what runs on my statements (no rows: nothing)
SELECT * FROM PREPROC_RT.INSTALLED_MODULES;      -- semantic_views v0.5.1; cast_shorthand, trailing_comma (0.3.1)
EXECUTE SCRIPT PREPROC.STATUS;                   -- resolution CURRENT, as a DBA
SELECT industry, approved_companies, pre_approved_amount
FROM CREDORA_SEM.PORTFOLIO GROUP BY industry ORDER BY pre_approved_amount DESC LIMIT 5;
```

To roll back, run `ALTER SYSTEM SET SQL_PREPROCESSOR_SCRIPT = NULL;` (it applies to new sessions, and the app's pooled sessions keep their setting until they reconnect). Semantic SQL then needs `EXECUTE SCRIPT SEMANTIC_ADMIN.ENABLE_SEMANTIC_SQL();` per session.

After role grants change, run `EXECUTE SCRIPT PREPROC.REFRESH;` (the deploy tool does).

Upgrading.

- For exasol-semantic-views, change `SEMVIEWS_VERSION` and its sha256 in `deploy/exasol_setup.py` and re-run `credora.py exasol`. The installer runs when the pin differs from `SEMANTIC_CATALOG.PRODUCT_VERSION`, with the system preprocessor off while it replaces the scripts, as the project's upgrade procedure asks.
- For preprocessor-framework, `release.sql` is a clean-install artifact, so the deploy tool runs it only when schema `PREPROC` does not exist, and records the release as that schema's comment. For a new release, run the framework's idempotent installer (`uv run preproc install` from its checkout at the new tag, as DBA), which keeps `PREPROC.CONFIG`, then update `PREPROC_VERSION`, its sha256 and the schema comment.
